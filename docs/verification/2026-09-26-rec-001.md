Mutation checks, each reverted immediately: removing the revision condition from update failed only the conflict test; removing the household filter from the detail query failed only the AC-02 recipe test; disabling the request-id lookup and uniqueness failed only the idempotency test.

New integration coverage (`tests/integration/recipes.test.mjs`): every preset saves through normal validation with provenance and no price; manual recipe with Unicode, decimal normalization, "to taste" lines and normalized ingredient keys; preset copy edited while `GET /api/recipe-presets` stays identical (AC-05); 24 invalid inputs return 400 and create nothing; sequential and concurrent retries with one `requestId` create one recipe; two members saving revision 1 concurrently yield one 200 and one 409, and a member may edit another member's recipe; archive/restore with stale-revision and wrong-state conflicts; AC-02 404s for list/create/read/edit/archive/restore across households, including a valid B recipe id under A's path; removed members lose access, and writes need the CSRF token; database constraints reject cross-household lines, unit without quantity, excess scale, unknown units and preset source without id.

The shared sign-in helpers moved from `auth.test.mjs` to `tests/integration/harness.mjs` without changing assertions; all 17 earlier tests still pass.

New browser coverage (`tests/e2e/recipes.spec.ts`, desktop and mobile): add a Unicode recipe with structured ingredients and a step, view it, edit it, archive, find it under Archived, restore; save a starter recipe as an editable copy with points; a stale edit shows the conflict message and "Load the latest version" loads the other change. `shell.spec.ts` now covers searching and inspecting the 12 starter recipes while signed out.

Found and fixed during verification: closing the recipe dialog while an archive/restore request was in flight let the response reopen it.
