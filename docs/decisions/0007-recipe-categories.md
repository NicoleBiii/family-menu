# ADR 0007 — Household recipe categories and AI category suggestions

Date: 2026-10-02. Status: implemented on `claude/ux-002-categories` (UX-002 phase 2). Source: the owner-approved [UI expansion proposal](../proposals/2026-10-01-ui-expansion.md) §3: one primary category per household recipe, household-owned categories, explicit confirmation of preset and AI suggestions.

## Decisions

- **Household-owned rows.** `app.recipe_categories` holds `id`, `household_id`, a display `name` (1–40 characters after trimming) and a `name_key` (NFKC, lower case, collapsed spaces, like `ingredient_key`). `unique (household_id, name_key)` means one household cannot have both "Soups" and "soups". At most 30 categories per household. Like the 500-recipe limit, this is a soft check without a lock, so concurrent creates can go slightly over it.
- **One nullable category per recipe.** `recipes.category_id` is nullable. A composite foreign key `(household_id, category_id) → recipe_categories(household_id, id)` keeps a recipe and its category in one household at the database level. Null means Uncategorised. The migration is additive: existing recipes stay Uncategorised and are never reclassified automatically.
- **Recipe writes.** `categoryId` is optional on create, preset and AI saves (omitted means Uncategorised). On a full-replacement update, an omitted `categoryId` keeps the current category, so a browser still running the previous bundle during a deploy cannot clear it; `null` clears it. A supplied id must belong to the household. It is read `FOR KEY SHARE` inside the write transaction, so a concurrent category deletion either waits for the save or makes it fail with 400, never with a foreign-key 500. Another household's id fails in the same way.
- **Shared management.** Every active member may create, rename and delete categories (shared-menu rule). Every route uses the existing membership check, takes the membership lock on writes, and returns 404 to non-members.
  - **Create.** Creating a name that already exists (by `name_key`) returns the existing category. The call is therefore idempotent, and accepting a suggestion twice creates one row.
  - **Rename.** Renaming is last-write-wins; categories have no revision, because a name is small and its links are by id. A rename keeps every recipe link. Renaming to another category's name returns 409.
- **Delete needs a destination.** `POST …/categories/:id/delete` requires `moveTo`: another category in the household, or `null` for Uncategorised. In one transaction it locks the category `FOR UPDATE` and moves every recipe in that category, archived ones included, to the destination. Each moved recipe gets `revision + 1`, `updated_by` and `updated_at`, so an editor open on it reports a conflict instead of saving a stale category. Then it deletes the row. The destination cannot be the category itself.
- **Order snapshots stay unchanged.** Orders snapshot the recipe name, servings, price and ingredients (ADR 0004). Categories are not in the snapshot, so category changes never rewrite an order.
- **Preset suggestions.** Each preset carries a fixed `category` key (`breakfast`, `mains`, `noodlesRice`, `soups`, `vegetables`). The interface shows that key as a name in the current interface language. If the household already has a category with that name in either language, the editor preselects it. Otherwise it offers "Create …" as an explicit action. Nothing is created silently. The key is metadata, not recipe text, so preset `version` numbers are unchanged.
- **AI suggestions.** The draft prompt now includes up to 30 household category names inside `<categories>` tags. Angle brackets and line breaks are stripped, and the system prompt treats the names as data. The model returns `category`: an existing name, a short new name, or null. Validation keeps a trimmed suggestion of 1–40 characters and otherwise drops it to null without failing the draft. The suggestion is stored as `suggestedCategory` in the draft JSON. On review, the editor preselects a matching household category. For a new name it offers "Create …", or the member picks another category or Uncategorised. A rejected suggestion creates nothing, and saving validates `categoryId` against the household like any recipe save.
- **Cost bound.** Category names add at most 30 × 40 characters plus separators to the prompt. The worst-case input estimate rises from 2,500 to 5,000 tokens, which allows two tokens per character for this extra text. The worst-case reservation becomes USD 0.0175 for Haiku 4.5, 0.0045 for DeepSeek Flash and 0.005 for Gemini 3.1 Flash-Lite. Household, personal and monthly-budget limits are unchanged.
- **Privacy.** Category names are household-authored text sent to the AI provider only when a member asks for a draft. No household name, member identity or recipe is added to the prompt. The interface's AI privacy note says that category names are included.

## Consequences and limits

- Meals browsing by category and the basket are UX-002 phase 3. This phase shows categories on the Menu (filter and management) and in the recipe editor.
- Two members who create different names for the same idea (for example "Soup" and "Soups") get two categories. Merging them is a delete with `moveTo`.
- Matching preset suggestions against household names covers only the English and Chinese names of the five preset keys.
